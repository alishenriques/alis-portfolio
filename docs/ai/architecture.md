# Architecture

## Repos (siblings under `~/repos`, GitHub owner `alishenriques`)

| Repo | Package | Role |
|---|---|---|
| `alis-portfolio` | (private app) | Next.js App Router front-end; main repo and source of these docs |
| `alis-portfolio-api` | `@alishenriques/portfolio-api` | GraphQL API and CMS backend |
| `alis-design-system` | `@alishenriques/design-system` | React component library published to public npm |
| *(future)* services site | (private app, repo not created yet) | Sales site for freelance services; consumes the same API and design system |

**Scope split (2026-10-06):** `alis-portfolio` is only the corporate career portfolio; freelance services move to the future services site (see "Scope" in [README.md](README.md)). The API and the design system are shared by both front-ends, so keep them generic: no portfolio-only assumptions in GraphQL types, resolvers or DS components.

## Data flow

Next.js (server components / route handlers) → Axios POST to `NEXT_PUBLIC_GRAPHQL_URL` → GraphQL Yoga → Drizzle → Neon Postgres. Images live in Cloudinary; the DB stores their URLs (`media` table).

Responses are parsed with Zod schemas on the front-end as well, even though the API already validates them.

## API (`alis-portfolio-api`)

- `src/app.ts`: `createApp(env)` builds the Yoga instance. Used by `src/index.ts` (local Node server) and `api/graphql.ts` (Vercel function). `vercel.json` rewrites `/graphql` to `/api/graphql`.
- `src/graphql/schema.ts`: SDL and resolvers. Domain models are in `src/schemas/domain.ts` (Zod, the source of truth for types).
- `src/db/schema.ts`: Drizzle tables (`profiles`, `projects`, `experiences`, `media`). Migrations are generated into `drizzle/` and applied with `yarn db:migrate`.
- **Fallback mode:** without `DATABASE_URL` the API serves data from `src/db/fallback.ts`; without Cloudinary credentials the upload client is `null`.
- **CMS auth:** mutations require header `x-cms-key` equal to `CMS_API_KEY`. Unauthorized returns a `GraphQLError` with code `UNAUTHORIZED`. Throw `GraphQLError` for client-visible errors: Yoga masks plain `Error`s. Invalid input becomes `BAD_USER_INPUT`; writes without a database become `DATABASE_UNAVAILABLE`.
- **CMS operations:** `updateProfile` (single profile row); `upsertProject` (replaces the project with that slug) / `deleteProject`; `upsertExperience` (create when `id` is omitted, update when given) / `deleteExperience`; `createUploadSignature` (signed params for direct browser uploads to Cloudinary; the secret never leaves the API).
- **`sendContactMessage`** (`SendContactMessageInput { name, email, message, website }`): the only **public** mutation — no `x-cms-key`. Sends via Resend (`src/lib/resend.ts`, same "returns `null` if unconfigured" pattern as Cloudinary; `EMAIL_UNAVAILABLE` if so). `website` is a honeypot: real visitors never see that field (hidden via CSS on the form), so a non-empty value means a bot filled every input — the resolver returns `true` (same response as a real send) **without** sending, so a bot can't distinguish "detected" from "sent". No other spam mitigation (no rate limiting/CAPTCHA) — a deliberate zero-infra trade-off for a portfolio's traffic level.
- **Visibility:** public `projects` / `project` return only published projects (`publishedAt` in the past), ordered by `sortOrder`. A valid `x-cms-key` also sees drafts. `experiences` has no draft concept — it's owner-authored, so every row is public; ordered by `sortOrder`, then most recent `startDate` first. Dates are `YYYY-MM` text (no fabricated day), validated by `yearMonthSchema`; `endDate: null` means the role is current.
- **Seed:** `yarn db:seed` upserts placeholder profile/project into the configured database (idempotent). Doesn't touch `experiences` — real data comes from the CMS once available.
- **Testing DB code:** tests use PGlite (in-memory Postgres) with the real migrations from `drizzle/` via `src/test/helpers.ts`; `createApp(env, { db, cloudinary })` accepts injected dependencies. `Database` is typed as the driver-agnostic `PgDatabase`.

## Front-end (`alis-portfolio`)

### Folder architecture

Mirrors the modular structure of the reference app `~/repos/awa-backstage-web` (see that repo's own docs for the original), translated from its Vite/react-router SPA idioms to Next.js App Router:

```
src/
  app/[locale]/       # routes only — every page.tsx is a thin wrapper delegating to a module (see below)
  i18n/                # next-intl config: routing.ts, navigation.ts, request.ts
  locales/             # pt.json, en.json — flat translation files, nested UPPER_CASE namespaces
  proxy.ts             # Next.js 16's middleware (renamed — see "Next 16 gotchas")
  modules/             # feature/page compositions, each self-contained
    home/, about/, experience/, skills/, layout/
    <module>/
      <Name>.tsx
      styles/index.styles.ts   # Tailwind class strings grouped in a plain object, not inline in JSX
      tests/<Name>.test.tsx
      components/<SubComponent>/...  # same Name/styles/tests shape, one level deeper
      constants/                     # config data (menu items, skill lists) kept out of the component body
  shared/
    components/<Name>/   # same Name/styles/tests shape — reused across modules, not generic enough for the DS
  lib/                 # non-UI: GraphQL client, schemas, small utilities (env.ts, graphql-client.ts, portfolio.ts, schemas.ts, format-date.ts, utils.ts)
```

A component/page that's only used by one module lives inside that module (`modules/home/components/Hero`); one used by two or more lives in `shared/components`; one general enough for other projects goes in `alis-design-system` instead (see below — several `shared`/`modules` pieces here are DS candidates once there's a second consumer, per the user: built here first for deadline reasons).

### i18n (`next-intl`, locale-prefixed URLs)

- Locales `pt` (default) and `en`, URLs `/pt/...` and `/en/...` (`src/i18n/routing.ts`). `/` redirects to the default locale.
- `src/proxy.ts` runs `next-intl`'s middleware for locale detection/redirect. **Not named `middleware.ts`**: Next.js 16 renamed that file convention to `proxy.ts` (deprecated but likely still functional either way — don't reintroduce `middleware.ts`).
- `src/app/[locale]/layout.tsx` is the **root layout** (renders `<html lang={locale}>`; there is no separate top-level `app/layout.tsx` — a root layout under a dynamic segment is an officially documented Next.js pattern for i18n). Wraps children in `NextIntlClientProvider` and the app's `Layout` (TopBar + Sidebar + ContactDialog, see below).
- Server Components call translations with `getTranslations()` (async, `next-intl/server`); Client Components and Server Components alike can use the `useTranslations()`/`useLocale()` hooks — `next-intl` special-cases these to also work in RSC (no `"use client"` needed just for translations).
- `src/locales/{pt,en}.json`: nested namespaces in `UPPER_CASE` (`NAV.HOME`, `HOME.FEATURES.TYPESCRIPT.LABEL`, `CONTACT.SUCCESS`), matching the reference app's key style. Rich/highlighted text (e.g. the hero subtitle) uses `next-intl`'s tag syntax (`<hl>...</hl>`) with `t.rich(...)`, not plain `{variable}` interpolation — the latter can't carry JSX.
- `src/i18n/navigation.ts` exports locale-aware `Link`/`usePathname`/`useRouter` (wraps Next's own); always import navigation from there, not `next/link` / `next/navigation`, so links keep the current locale prefix.
- `ExperienceItem` formats dates via `formatDateRange(start, end, locale, presentLabel)` — month abbreviations and the "current role" label both vary by locale (`src/lib/format-date.ts`).

### Layout: terminal nav on desktop, drawer below `lg`

- `src/modules/layout/Layout.tsx`: wraps every page with `ContactDialogProvider` + `TopBar` + the page + `ContactDialog`.
- `TopBar`: sticky 3-column header (`grid-cols-[1fr_auto_1fr]`, so the centre stays centred). Below `lg`: hamburger (left), logo (centre), `LanguageSwitcher` (right). From `lg` up: logo (left), `DesktopNav` (centre), `LanguageSwitcher` + `ContactButton` (right). It owns the drawer's open state.
- `DesktopNav` (`modules/layout/components/DesktopNav`): the header menu on desktop, styled as a shell prompt (`$ ~/início ~/sobre …`). Hover/focus slides a `>` in, nudges the label and blinks a cursor; the current page (`aria-current="page"`) keeps a blinking cursor. Motion is disabled under `prefers-reduced-motion` (`motion-reduce:` variants); the `blink` keyframe lives in `globals.css`. Prompt glyphs are `aria-hidden`.
- `ContactButton`: the desktop header CTA that opens the contact dialog (the drawer has its own copy of the action).
- Menu items live in `modules/layout/constants/menuConfig.ts` and feed both `DesktopNav` and `Sidebar`.
- `Footer` (`modules/layout/components/Footer`): site-wide, rendered by `Layout` after the page. Copyright plus GitHub/LinkedIn icon links (`constants/socialLinks.ts`, `FOOTER.*` labels), accent-coloured. LinkedIn's mark is inlined (`LinkedinIcon.tsx`) because Simple Icons dropped that brand.
- `Sidebar` (`modules/layout/components/Sidebar`): a controlled (`isOpen`/`onClose`) animated slide-in/out overlay drawer, shown only below `lg`; the trigger is in `TopBar`. **It must stay a sibling of `<header>`, never inside it**: the header's `backdrop-blur` makes it the containing block for `position: fixed` descendants, which pinned the drawer to the header's height (the overlap bug). While open it locks body scroll and closes on Escape/backdrop/link click. The drawer stays mounted and slides off-screen via a CSS transform, with `aria-hidden` toggled on the closed `<aside>` for accessibility — tests rely on `aria-hidden` exclusion (`queryByRole` returns null for hidden content), not `toBeVisible()`, which doesn't account for transforms.
- The `⌘K` **CommandPalette is intentionally unused right now** (removed from the visible nav, replaced by the Sidebar), but its code stays in `alis-design-system` — the plan is to repurpose it later as an actual search feature. Don't delete it.
- `ContactDialog` (`modules/layout/components/ContactDialog`): opened from anywhere via `useContactDialog()` (`modules/layout/ContactDialogContext.tsx`, a small React Context — justified here because both the Sidebar's "Contact" item and any future CTA need to open the same dialog without prop drilling). Client-side Zod validation (`contactFormSchema` in `lib/schemas.ts`) mirrors the API's; submits via `sendContactMessage()` (`lib/portfolio.ts`) straight from the browser to the GraphQL API (public mutation, no CMS key). Has a hidden honeypot field (`website`) for basic spam mitigation — see the API section.

### Home page composition

- `app/[locale]/page.tsx` → `modules/home/Home.tsx`: `Hero` (logo, eyebrow line "Alisson Henriques · Desenvolvedor Front‑End Sênior", the headline "Arquitetura de front‑end que escala — construída com engenharia e IA." in the Archivo display face with a `<hl>` highlight, `GrowthTrace`, rich-text subtitle, email/phone contact row, `TaglineHighlights`, decorative `ParallaxPanels`) → `FeatureChips` ("O que eu valorizo" / "What I value": a titled, centred flex-wrap section with the 10 value props (5 per row from `lg`, 3 from `sm`, 2 below; a partial last row stays centred), icon above text) → `Skills` (`modules/skills`, real primary stack rendered with official brand icons from `@icons-pack/react-simple-icons`; 15 techs grouped by area in `skillsList.ts`; brand colours are overridden where the package's own hex vanishes on the dark ground — Angular `#DD0031`, JWT `#D63AFF`, CSS3 `#1572B6`, Next.js white. Layout: centred flex-wrap, three rows of 5 with dividers from `lg`). No longer has a Projects section — see "Projetos page" below.
- `GrowthTrace`: decorative SVG line chart under the headline that draws itself (`pathLength` normalised to 1, `draw`/`pop` keyframes in `globals.css`) then pops a marker; disabled under `prefers-reduced-motion`.
- `TaglineHighlights`: the four highlight phrases (`HOME.TAGLINE.*`: modern interfaces, performance, scalability, AI-assisted software engineering) as pill chips, each with a small custom inline SVG icon (`icons.tsx`, currentColor + accent details) and hover motion. Not lucide: these are bespoke on purpose.
- `ParallaxPanels` (`modules/home/components/ParallaxPanels`): two decorative "floating window" panels (a code snippet, a file tree) that tilt toward the pointer on `pointermove`, RAF-throttled. Skipped entirely (no listener attached) under `prefers-reduced-motion: reduce` or `(pointer: coarse)` (touch). Purely `aria-hidden` — not real content.
- **Hero is a two-slide toggle** (`Hero.tsx` is now `"use client"`, `useState<number>` for the slide index): the `</>` glyphs flanking the headline are the prev/next controls (`aria-label`, not relying on their visible glyph as the accessible name — same pattern as `Timeline`'s own aria-label fix). Slide 0 is the original dev-hiring pitch (headline/subtitle unchanged); slide 1 is **AI-assisted development** ("Programação assistida por IA com precisão arquitetural", subtitle about product/business vision and shipping faster without losing quality). It replaced the earlier freelance-services slide (and its four service chips) after the 2026-10-06 scope split, which sends services to a separate site. The headline/subtitle block, the growth-chart SVG's color, the background glow and the `ParallaxPanels` decorations swap between slides (text is `key`-remounted with a `slide-reveal` fade/settle keyframe in `globals.css`, skipped under `prefers-reduced-motion`); identity chrome (logo, eyebrow, email/phone contact row) stays constant across both.
  - **Slide 1's accent is blue (`#38bdf8`)** — the one deliberate departure from the site's single-lime-accent (`--ds-color-accent`) palette, per the user, inspired by their own terminal's prompt colors. Defined inline at each use site (title/subtitle highlight, background glow, the AI decorations' charts and robot eyes), not promoted to a `--ds-*` design-system token: it's a one-off, portfolio-specific creative choice tied to this single feature, not something other consumers of the DS need (see `conventions.md`'s reusable-vs-local rule). `GrowthTrace` (the decorative SVG line under the headline, previously hardcoded to the DS accent) gained an optional `color` prop — a CSS custom property (`--growth-trace-color`) set inline and referenced with a `var(..., var(--ds-color-accent))` fallback in its own CSS-module classes — so Hero can pass the same blue for slide 2, keeping the whole slide (not just the text) visually consistent.
  - **`ParallaxPanels` has one decoration set per slide** (`variant: "code" | "ai"`): `"code"` is the original code-editor + file-tree windows; `"ai"` is six logo tiles from `LOGO_TILES` (large: Anthropic via `SiAnthropic` and OpenAI via the inlined `OpenaiIcon`, since Simple Icons dropped that brand, same approach as `LinkedinIcon`; small: Claude, Cursor, GitHub Copilot, v0), an 8-bit `PixelRobot` (drawn from a character grid in `ROBOT_PIXELS`, merged into one rect per same-color run by `toPixelRuns`) and two agile charts (sprint burndown, velocity bars). Both sets stay mounted and crossfade on `variant`. Every element is a `Floating` wrapper carrying `data-parallax`/`data-rotate`/`data-depth`; the single pointer listener moves them all through `parallaxTransform`, so adding a decoration needs no new ref or effect code. Desktop only (`lg:`), static on touch and under reduced motion.
  - **Background crossfade**: two full-cover radial-gradient glow layers (lime, blue) stacked with `opacity` transitions — plain `background` isn't reliably cross-browser-animatable between two different gradient functions, but two overlapping layers whose opacity each transitions independently are.
- `Sobre`/`Corporativo`/`Projetos` are their own routes (`app/[locale]/sobre`, `app/[locale]/corporativo`, `app/[locale]/projetos` → `modules/about`, `modules/experience`, `modules/projects`) — **not** anchored sections on the home page. Contato is still the dialog, not a page.
- **`Corporativo` (renamed from "Experiência")**: work history scoped to private-sector roles only, via a new `Experience.isCorporate` boolean (`NOT NULL DEFAULT true`, migrated on the live Neon DB) — real entries that aren't private-sector company work (e.g. the Tribunal Regional Federal da 1ª Região public-sector internship) still exist in the data but are filtered out client-side (`allExperiences.filter((e) => e.isCorporate)`), not deleted. Mirrors `Project.featured`'s precedent exactly: a simple CMS-editable boolean scoping one curated page view, rather than a frontend name blacklist. The page also picked up a continuous timeline rail (marker + connecting line down the list, the same "line spans the item's own `padding-bottom`, not a flex `gap`, so it structurally reaches the next item's marker" CSS technique the DS `Timeline` uses — reapplied locally here rather than via the DS component itself, since it's a simple, tightly page-specific effect, not a generically reusable one) and content-width/font-color fixes matching the About page (same "inner element had its own narrower `max-w`/muted color than the page root" bug fixed there once already).
- `About` shows a "Formação" (education) line below the headline — `ABOUT.EDUCATION_LABEL`/`EDUCATION_VALUE`, static i18n copy, not a `Profile` field. Deliberate: unlike `bio`/`headline`/`name` (CMS-editable, meant to change without a deploy), education is effectively permanent, one-time biographical content, so it doesn't warrant a DB column + GraphQL field + migration for something this static.
- `Profile.bio` supports a small amount of inline/block markup, parsed by `lib/richText.tsx` — not a full Markdown renderer, just what this one field needs, all standard Markdown syntax on purpose (nothing new to learn when editing the bio): `**bold**` → `<strong>` (`renderInlineMarkup`), a paragraph starting with `> ` → the DS's `Quote` (`parseBio`), and a line starting with `## ` → a heading block with a slugified `id` (`parseBio`/`getBioHeadings`). `About` maps `parseBio(bioText)` to `<p>`/`<Quote>`/`<h2 id=…>` blocks, builds a table of contents from the headings, and shows `estimateReadingMinutes(bioText)` (~200 words/minute) above the text.
- **`headline`/`bio` are genuinely bilingual, unlike `Experience`'s content fields** (`company`/`role`/`description` are single Portuguese-only columns — switching to `/en` there only changes the surrounding UI chrome: labels, date formatting — never the actual experience text). `Profile` gained nullable `headlineEn`/`bioEn` columns; `About` calls `getLocale()` (`next-intl/server`, the Server Component counterpart to the `useLocale()` hook used elsewhere) alongside `getTranslations`, and `pickLocalized(locale, pt, en)` — a two-line helper local to `About.tsx` — returns the English text only when the locale is `en` *and* a translation exists, falling back to the Portuguese text otherwise. That fallback is deliberate: `headlineEn`/`bioEn` can be left unset without breaking the English page or blocking `headline`/`bio` edits on a translation existing first.
- Bio quotes render inline (`<Quote className={styles.quoteSpacing}>`, no `float`), each with its own `margin-bottom` for spacing. The DS `Quote`'s `float="left"/"right"` prop was tried for a side-floated, margin-note look, but the user found it hurt readability once seen in production, so `About.tsx` went back to keeping every quote inline — the DS still exposes the prop (kept as a generically useful capability), it's just unused here.
- `About`'s avatar is the DS's `Avatar` component (`objectPosition="top"`, not the default centred crop): the source photo is a 960×1280 portrait, and a centred square crop clips the hairline — anchoring to the top keeps the whole head in frame, in both the thumbnail and the expanded view. Click it to expand into a large, centred, blurred-backdrop overlay with a zoom-in transition (round crop, just bigger) — closes via the × button, a backdrop click, or Escape.
- `About` also renders `shared/components/VideoEmbed` (16:9 frame, `youtubeId`/`title`/`comingSoonText` props): with no `youtubeId` yet (the user hasn't recorded/uploaded the video), it shows a dashed-border, dot-grid placeholder with a play icon and `comingSoonText`, in the exact frame the real `youtube-nocookie.com` embed will use — so the final layout is visible before the video exists. Set `youtubeId` on the `<VideoEmbed>` call once the video is on YouTube; no other changes needed.
- All pages are marked `export const dynamic = "force-dynamic"` — required because the GraphQL calls go through Axios, not Next's `fetch`, so Next can't detect they're dynamic on its own; without this the build tries (and fails) to fetch data at build time.

### Projetos page: a GitKraken-style timeline

`app/[locale]/projetos/page.tsx` → `modules/projects/Projects.tsx` (Server Component, fetches `getProjects()`) → `ProjectsTimeline` (Client Component, `modules/projects/components/ProjectsTimeline`): owns which project is selected (`useState<string | null>`, keyed by `slug` — the public, stable identifier, not the database `id`) and renders the DS `Timeline` alongside `ProjectDetailPanel`. Split out of `Projects` because selection state needs a Client Component, while data-fetching stays server-side like every other page.

- **Deep-linking a project's panel open** (`?project=<slug>`, used by the About page's showcase below): `page.tsx` reads the `searchParams` prop (a `Promise` — Next 16, must `await`) and passes `initialSelectedSlug` down through `Projects` to `ProjectsTimeline`, which seeds its `useState` with it. No `useSearchParams()` client hook, no `Suspense` boundary needed — the `searchParams` page prop is the documented way to read query params from a Server Component, and this route is already `force-dynamic`.
- `Timeline` (DS): a vertical, GitKraken-style commit graph — stacked, clickable nodes (`iconUrl` or a fallback initial) connected by colored lines, in the order the API returns (`sortOrder` asc, then `publishedAt` desc — newest first, like a real commit graph). Each node's line color comes from a golden-angle hue rotation (`137.508°` per index) computed inside the component, not a fixed palette or a DB field — so any number of projects stays visually distinct. Controlled: `items` (`id` is the project's `slug`), `selectedId`, `onSelect(id)`.
  - **Each row reads like a commit line** (`0.9.0`, per the user: "levando essa ideia como se fossem commits"): `TimelineItem` gained optional `typeLabel`/`description` (`ProjectsTimeline` passes `project.projectType`/`project.summary`) — name, then a small generic tag icon + type, then "– " + description, one wrapping flex line (`flex-wrap`, not a rigid single line) that breaks gracefully on narrow viewports. The tag icon is a plain hand-drawn glyph, not per-`typeLabel`-value, since `projectType` is free text with no fixed set of values to map icons to.
  - **`0.9.1` fixed a real accessibility bug**, found by dumping the actual accessibility tree, not assumed: the visual `|`/`–` separators are `aria-hidden`, and an `aria-hidden` element contributes *no whitespace* to name computation either — two adjacent visible spans (label, description) came out concatenated with zero space between them ("ASummary", not "A Summary"). Fixed with an explicit `aria-label` built from `label`/`typeLabel`/`description` joined with `" — "` on the button itself, with the whole visual `.content` span hidden from the accessibility tree so only that string is ever read — sidesteps the whitespace-in-child-node-computation problem entirely rather than patching around it.
  - **`0.9.2` fixed a real (vertical, not horizontal) layout bug**: `.button`'s `align-items: center` vertically centers the node against its sibling content — fine while that content is shorter than the node's 48px, but a project whose description wraps onto 2 lines makes the content taller, so centering pushes the node *down*. `.line`'s `top` stays hardcoded to the node's own height (assuming the node sits flush at the row's top edge), so it kept starting at the node's old position — now overlapping the node that had moved down. First reported as the connecting line looking "misaligned" with the node horizontally; disproven with `getBoundingClientRect` measurements (0px horizontal offset at several zoom levels) and even a pixel-level scan of the user's own screenshot, both showing perfect horizontal centering — the *vertical* overlap only became clear once the user sent a DevTools screenshot with the line element selected, showing its computed box starting above the node's actual (shifted-down) position. Fixed with `align-items: flex-start` (the node now always stays flush at the top, matching the usual avatar-next-to-a-multi-line-paragraph convention) — verified against a live build hitting the real production API (8.75px overlap before, 0px after, every row) before publishing.
  - **`0.9.3` fixed a second, distinct bug in the same area — paint order, not layout**, found by the user via DevTools even after `0.9.2` measured a genuine 0px gap: `.line` is `position: absolute`, and per CSS stacking rules a positioned element with `z-index: auto` always paints *above* static-flow content regardless of DOM source order — so the line kept painting over the node's decorative `box-shadow` (a 4px halo drawn outside its layout box, which `getBoundingClientRect` can't see) wherever the two met. Fixed by dropping that box-shadow and giving the node/line explicit stacking (node `z-index: 2`, line `z-index: 1`), so the node reliably paints in front. General lesson: a 0px layout gap between two elements doesn't rule out a visual collision — also check `position`/`z-index`/DOM order, and whether either element's visual footprint (box-shadow, outline, border) extends past its own layout box.
- `SidePanel` (DS): the sliding lateral drawer itself — `open`/`onClose` controlled, stays mounted while closed (CSS transform + `aria-hidden` + `inert`, the same convention as the portfolio's own `Sidebar` drawer) so the close transition plays too, not just the open one.
- `ProjectDetailPanel` (portfolio, `modules/projects/components/ProjectDetailPanel`): the content inside the `SidePanel` — home-page screenshot (`coverUrl`), title, `projectType`, `tags` (DS `TagList`), a status dot for `isActive` ("Site ativo"/"Site fora do ar"), `summary` as a short line, `body` split on blank lines into paragraphs as the fuller bio, and a "Visite o site" link (`siteUrl`, `target="_blank" rel="noopener noreferrer"`) when set. Content-specific, so it stays in the portfolio; only the drawer shell is in the DS.
- `Project` gained four fields for this page (`alis-portfolio-api`'s `src/db/schema.ts`/`schemas/domain.ts`/`graphql/schema.ts`, mirrored in this repo's `lib/schemas.ts`): `iconUrl` (small timeline-node logo, distinct from `coverUrl`), `projectType` (free text, e.g. "E-Commerce" — not an enum, the set of kinds isn't fixed), `siteUrl`, `isActive` (`NOT NULL DEFAULT true`).
- The Home page's old `#projetos` anchor section is gone; `NAV.PROJECTS` now points straight at `/projetos` (`menuConfig.ts`), matching how `Sobre`/`Experiência` already work.
- Real projects seeded so far, all from case-study documents the user provided (content, tags, stack, a real home-page screenshot as `coverUrl`, and a real brand-logo `iconUrl`, all uploaded to Cloudinary) rather than hand-written: **Respire C'alma** (respirecalma.eco.br, an e-commerce for a São Paulo therapeutic-candle/aromatherapy brand maintained since 2021 — the only one currently `featured: true`), **Galeria Patricia Costa** (galeriapatriciacosta.com.br, an art-gallery site in Rio de Janeiro live since late 2025 — the logo arrived in two rounds: a first crop from the case study's screenshot was too blurry to use, then a proper logo file, then a *higher-resolution* version of that same file replacing it again — `iconUrl` is a Cloudinary URL, so swapping it is just another `upsertProject` call, no code change), **Um Banhado Digital** (academiadecuradoria.com.br/umbanhadodigital, a chat-with-an-AI-styled digital art exhibition for the Academia de Curadoria and MALG/UFPel, Oct–Dec 2024, icon is the Academia de Curadoria's own logo), and **Migrações Leste-Sul** (sites.usp.br/mac_migracoes, an international conference site for MAC USP running Nov 2026, icon is the MAC USP wordmark — initially skipped since the mark inside the case study's own screenshot wasn't cleanly croppable, added once the user sent the logo file directly).

### About page: "Conheça alguns dos projetos que criei"

A closing section on the About page (`modules/about/components/ProjectsShowcase`), three DS `ShowcaseCard`s picked from the same `getProjects()` data the Projetos page uses (fetched once more inside `About()`, in parallel with `getProfile()`).

- `pickShowcaseProjects(projects, count, random = Math.random)` (colocated `pickShowcaseProjects.ts`, unit-tested with an injected deterministic `random` so shuffle order doesn't make the tests flaky): filters to projects with a `coverUrl` (a card with no screenshot doesn't make sense here), always puts the `featured` project first if one exists, then fills the rest with a `Math.random()`-shuffled sample of the others — a fresh pick on every request, since `About` has no caching. **`featured` is this section's "pin the first card" mechanism** — it had no other live use in the app (the Home page's old projects section, its one other reader, was removed when `/projetos` shipped), so it was repurposed rather than adding a new field for the same idea; documented on the SDL in `alis-portfolio-api`. Exactly one project (`Respire C'alma`) is `featured: true` on the live DB right now — change which one via `upsertProject`.
- `ShowcaseCard` (DS, redesigned three times after the user saw it live): the image sits in its own fixed-ratio block (`aspect: 8/5`, close to the source screenshots' own 1440×900 shape) framed like a browser window — a solid (not gradient) chrome bar with traffic-light dots and an address bar showing `siteLabel`, echoing the browser-chrome mockups already used in these same projects' case-study documents. Title and a couple of tags sit *below* the image, on the card's own solid background — always legible, unlike text overlaid on an arbitrary screenshot. The description and a `footer` slot (left to the consumer rather than an `href`/`linkLabel` pair, so the DS component stays framework-agnostic while the portfolio still gets its own locale-aware `Link`) stay collapsed and slide open on hover/focus (CSS `grid-template-rows: 0fr → 1fr`, so the reveal fits whatever height the content needs without a guessed `max-height` — and the card *grows* to fit it, rather than being locked to a fixed height it could overflow). A real focusable element in the footer slot is what makes the reveal keyboard-reachable too (`:focus-within`), not just mouse-hover. Keeping the description/link *hidden* at rest (only the image, title and a tag or two show) is what solves the original "too tall, uneven between cards" complaint — the resting grid is compact and near-uniform no matter how much a given project's copy runs.
  - **First redesign** (0.8.0, replacing the original always-everything-visible layout — "cards estão cumpridos e esteticamente nada agradável... o efeito tá legal mas não foi tão impactante"): title/tags/description all overlaid on the image inside a fixed square, description hidden until hover.
  - **Second pass** (0.8.1, a real bug found by actually looking at the rendered result, not just the code): the square's gradient chrome scrim wasn't opaque enough, so the fake address bar visibly collided with whatever the real screenshot showed at its own top edge; and with 3 tags each wrapping onto their own line, the revealed content was taller than the fixed square, so on hover it overflowed *upward* past the card's own top edge and got clipped — the title disappeared entirely. Fixed by moving title/tags off the image (solid background instead) and dropping the fixed-square constraint in favor of a card that grows to fit its content.
  - **Third pass** (0.8.2, the user's own devtools measurements this time — a card body rendering at 217×151px, two tags each wrapping onto their own line, and the footer link wrapping onto two): the DS `TagList` reuse was dropped in favor of a local, deliberately smaller/boxier tag chip (11px mono, tight padding, 6px radius) — `TagList`'s pill shape and padding are shared by every other consumer and stayed as-is there — and the card body's padding was trimmed from `--ds-space-4` to `--ds-space-3`. Portfolio-side, the footer link's font size dropped to 10px and its letter-spacing was loosened, so both tags and the link fit on one line at this card's narrow width.
- Always revealed under `@media (hover: none)` (touch devices have no hover to trigger it) — every other DS component's touch-vs-mouse handling in this codebase disables motion for touch (`ParallaxPanels`'s `(pointer: coarse)` check); this is the first case that instead changes *what's shown*, since hidden-until-hover content would otherwise be permanently unreachable on a phone. Verified with Playwright's actual device emulation (`devices["iPhone 13"]`), not just a resized viewport — a resized desktop viewport still reports `hover: hover` (a real mouse is still available), so it's not a substitute for testing this media query.
- The hover motion: the image sits desaturated (`grayscale(0.55)`) at rest and comes into full color on hover, the card lifts with an accent-glowing border, the traffic-light dots flip from muted to their real red/yellow/green (a small "the window is waking up" detail), and the reveal panel slides open. All CSS transitions, skipped under `prefers-reduced-motion`, in keeping with the design system's stated motion philosophy (`architecture.md`'s "Motion" bullet, under Visual direction). The very first version of this component also had four corner brackets that snapped into place like a camera viewfinder — dropped in the first redesign; between the browser-chrome framing and the reveal panel there was already enough going on.
- The grid uses `items-start`, not the CSS Grid default `stretch` — with `stretch`, one card's hover-reveal growing taller would drag its row siblings to the same height too (grid track sizing responds to the tallest item, and `stretch` forces every item in that row to fill it). `items-start` lets each card size to its own content independently.
- `ProjectsShowcase` derives `siteLabel` from `project.siteUrl` (`new URL(...).hostname`, stripping `www.`) and caps `tags` to 2 before handing them to the card — both portfolio-side shaping, not the DS component's concern.
- Each card's footer links to `/projetos?project=<slug>` via `Link` from `@/i18n/navigation` (locale-prefixed automatically) — opening `/projetos` with that exact project's `SidePanel` already open, via the deep-link mechanism described above. The arrow next to the link nudges right on hover/focus using a plain Tailwind `group`/`group-hover:` pair scoped to the card's own root element (passed in via `ShowcaseCard`'s `className` prop) — not a design-system feature, just the portfolio's own CSS reacting to the same hover state the DS component already exposes.
- Renders nothing (`return null`) when there are no eligible projects (e.g. local fallback mode with no `coverUrl` set), rather than showing an empty heading.

### Loading feedback: full-screen overlay by default, per-button for forms

`shared/components/LoadingOverlay` is a full-screen blurred backdrop with the logo animating in the centre (the monogram breathing inside a spinning dashed ring, a blinking accent-coloured cursor after a terminal-style `$ carregando` caption — reusing the header nav's cursor-blink treatment). It has no hooks beyond `useTranslations` (works as a Server Component) and no visibility logic of its own — two independent callers decide *when* to show it, covering the two different ways the screen could otherwise sit frozen with no feedback:

1. **Route navigation** (`app/[locale]/loading.tsx`): Next's `loading.js` file convention wraps `page.tsx` and its nested routes (`sobre`, `experiencia`) in a Suspense boundary, shown automatically while that page's Server Component fetches data from the API. Needs no state — Next shows/hides it based on the Suspense boundary.
2. **Client-side requests, by default** (`modules/layout/components/HttpActivityOverlay`, mounted once in `Layout`): a Client Component subscribed via `useSyncExternalStore` to `lib/httpActivity.ts`, a small vanilla store (no React import, safe in both bundles) that `graphql-client.ts`'s axios request/response interceptors increment and decrement. The server-side data fetching in (1) runs in a separate module instance in the Node process and never touches this counter — no cross-contamination between the two mechanisms.

The overlay's `z-[70]` sits above the `ContactDialog` (`z-[60]`) on purpose: "blur over the whole screen" was taken literally, so a request made while the dialog is open still blurs over it too, briefly.

**Forms opt out and use the design system's `LoadingButton` instead** — blurring the whole screen (including the form itself) over a small inline submission is worse UX than feedback right on the button. `graphqlRequest(schema, query, variables, { trackGlobalLoading: false })` skips `beginHttpRequest`/`endHttpRequest` for that one call (a `trackGlobalLoading` field added to axios's `AxiosRequestConfig` via TS module augmentation in `graphql-client.ts`, read by both interceptors; defaults to tracked). `sendContactMessage` passes this. `LoadingButton` takes `isLoading` and a `loadingText` prop and, while loading, overlays a dark-fill/accent-border look on top of the consumer's own `className` and swaps its children for `$ {loadingText}` with the same blinking cursor as `LoadingOverlay`/`DesktopNav` — idle appearance stays whatever the consumer already had. It lives in `alis-design-system`, not this repo (see "Design system" below and `conventions.md`): nothing about it is portfolio-specific.

### SEO: metadata, sitemap, robots, Open Graph images

- `src/lib/seo.ts` is the single list of indexable pages (`SEO_PAGES`: `HOME`, `ABOUT`, `CORPORATE`, `PROJECTS` → their locale-less paths). A new public page gets an entry there, an `SEO.PAGES.<KEY>` block (`TITLE`, `DESCRIPTION`, `OG_HEADLINE`) in both locale files, a `generateMetadata` calling `getPageMetadata(params, "<KEY>")` (`lib/pageMetadata.ts`), and an `opengraph-image.tsx` calling `ogImageRoute("<KEY>")`. The sitemap picks it up from `SEO_PAGES`.
- The root layout's `generateMetadata` sets `metadataBase` from `NEXT_PUBLIC_SITE_URL` (Zod default: the production Vercel URL), a `%s | Alisson Henriques` title template, the default description and `robots`. Each page sets title, description, `canonical`, hreflang alternates (`pt-BR`, `en`, `x-default` → pt) and the full `openGraph`/`twitter` objects: Next merges metadata **shallowly**, so a page's `openGraph` replaces the layout's rather than extending it. The home page uses `title.absolute` because its title already names the site.
- `app/sitemap.ts` and `app/robots.ts` live outside `[locale]` (served at `/sitemap.xml` and `/robots.txt`; the proxy matcher skips paths with a dot). Both are thin wrappers over `buildSitemap`/`buildRobots`, which are unit-tested.
- Open Graph images are generated per page and locale with `next/og` (`lib/og/OgCard.tsx` is the card, `lib/og/ogImageRoute.tsx` the route). They use `generateImageMetadata` (one image, id `og`) only so the `alt` text can be translated; the plain `alt` export can't vary by locale. Next copies them to `twitter:image` on its own. Satori takes inline styles only, so the card hardcodes hex values mirroring the `--ds-color-*` tokens. Fonts are static `.woff` files in `src/assets/fonts` (Archivo 800, IBM Plex Mono 500, both SIL OFL, licences alongside); Satori can't read woff2 and `next/font` doesn't expose font files.

### A real bug this surfaced (worth remembering)

`event.currentTarget` in a React event handler is only valid for the **synchronous** part of the handler — re-reading it after an `await` returns `null` (per the DOM event dispatch spec; React doesn't special-case this). `ContactDialog`'s submit handler originally called `event.currentTarget.reset()` *after* `await sendContactMessage(...)`, which threw and silently flipped a successful send into the shown "failed" state. Fix: capture the element you'll need (`const form = event.currentTarget`) before any `await`, and use that captured reference afterward. General rule: never touch `event.currentTarget`/`event.target` after an `await` in a handler.

## Design system (`alis-design-system`)

Vite library build (ES module + `.d.ts`), React as peer dependency (externalized in the Vite build, not bundled). Styling via CSS Modules and tokens in `src/tokens.css` (`--ds-*`) plus decorative utility classes in `src/patterns.css` (e.g. `.ds-dot-grid`), both imported once as a side effect from `src/index.ts`. Consumers import `@alishenriques/design-system` and `@alishenriques/design-system/styles.css`. The portfolio's `next.config.ts` lists it in `transpilePackages`.

**Components:** `Avatar` (expandable circular photo — used by `About`), `Button`, `Eyebrow` (small muted uppercase label), `LoadingButton` (per-button terminal-styled loading state), `TagList` (used by `Projetos`'s `ProjectDetailPanel` — `ShowcaseCard` renders its own smaller, boxier tag chip locally instead, not this component), `Timeline` (GitKraken-style vertical commit graph — stacked clickable nodes, golden-angle-rotated connecting line colors), `SidePanel` (sliding lateral drawer) and `ShowcaseCard` (browser-window-framed media card — image, title, tags, description, a free footer slot — that reveals its description/link on hover/focus) — the first three built for and used by `Projetos`, `ShowcaseCard` by the About page's project showcase, see the sections above. `Panel` (raised bordered surface, optional dot-grid background), `TerminalPrompt` (mono prompt line with a blinking cursor), `PipelineBadges` (chips for real CI/test facts), `StatGrid` and `CommandPalette` (⌘K-triggered filterable overlay) — built for the original Console-only hero, **not used by the current mockup-driven Home** (superseded by `FeatureChips`/`Skills`/`Sidebar`), kept in the DS as they're still generically useful (e.g. `CommandPalette` is earmarked for a future search feature; see "Layout" above). All presentational/generic (content comes from props, no hardcoded copy), so they stay reusable beyond this one portfolio. See `conventions.md` for the rule on what belongs here vs. in the portfolio app.

**Four build gotchas worth knowing before touching this package again:**
1. **`"use client"` gets stripped by Rollup.** `CommandPalette` needs client hooks, but Vite/Rollup's library build silently drops the inline `"use client"` directive from `dist/index.js`. Since the whole package bundles into one file anyway, the fix is a Rollup output `banner: '"use client";'` in `vite.config.ts` — re-added unconditionally, so the *entire* bundle is client-boundary. That's fine here (no server-only code in this package) but re-check this if the library ever needs a server-only export. Verify after any build with `head -1 dist/index.js`.
2. **Local cross-repo testing needs a real tarball, not `portal:`/`file:` to the source dir.** Yarn's `portal:` protocol (or pointing `file:` at the repo directory) resolves Node's module graph against the *design system's own* `node_modules/react` (installed there for its own test suite), which is a second React copy from the portfolio's — causes "Invalid hook call" the moment a DS component uses a hook. `Button` never surfaced this because it has no hooks. The real npm-published package never has this problem (no `node_modules` in the published tarball, so the consumer's own React is what resolves). To test a local, unpublished DS change from `alis-portfolio`: run `yarn pack --out alis-design-system.tgz` in `alis-design-system`, then depend on `"file:../alis-design-system/alis-design-system.tgz"` in the portfolio temporarily — this is what a real npm install will actually contain, unlike a live source link. **Never commit that `file:` dependency**: it doesn't resolve on Vercel or any other machine. Revert to the published `^x.y.z` version before committing/deploying.
3. **`backdrop-filter` + a `-webkit-` fallback can vanish under Next's production CSS minifier.** `Avatar`'s backdrop originally declared both `backdrop-filter: blur(20px)` and `-webkit-backdrop-filter: blur(20px)`; Next's minifier (Lightning CSS) treated them as duplicates and kept only the prefixed one in the production bundle, silently disabling the blur in Chromium (`getComputedStyle(...).backdropFilter` came back `"none"` — confirmed, not guessed). Fix: declare only the unprefixed `backdrop-filter`. If a component ever needs the `-webkit-` fallback for older Safari, verify with `getComputedStyle` against the *portfolio's production build* (`yarn build && yarn start`), not just the DS's own dev server — a dev build won't reproduce this.
4. **A portfolio Tailwind class can never override a DS CSS-module rule of equal specificity, no matter the import order.** Tailwind v4 (`@import "tailwindcss"` in `globals.css`) wraps its own utilities in `@layer utilities`; the DS's CSS Modules (e.g. `Quote`'s `margin: 0`) are plain, unlayered CSS. Per the CSS cascade-layers spec, *any* unlayered normal-priority rule beats *any* layered normal-priority rule, regardless of specificity or which stylesheet loads last — so passing e.g. `className="mb-10"` to `<Quote>` silently computes to `margin-bottom: 0` in production (confirmed via `getComputedStyle`, not guessed — this is exactly what happened when `About.tsx` tried it for spacing below a bio quote). The portfolio's own conventions.md rule about DS-overriding-consumer already covers the mirror-image case; this is the same fix in the other direction: pass an inline `style` prop instead of a className whenever the portfolio needs to override a DS component's own CSS-module property — inline styles win over any stylesheet, layered or not.

## Visual direction (locked 2026-09-22)

"Console" — an engineering/dev-tool aesthetic, not an animated showcase. Rationale: the audience is senior front-end / architecture hiring, who respond to demonstrated technical rigor (real CI status, real test counts, clean typography, fast/native-feeling mobile) more than motion effects. Two directions were prototyped and compared; "Console" won, with the bold accent-highlighted headline treatment merged in from the runner-up. Prototype: https://claude.ai/artifact/WjWaEenJaw8ScKKHT3QuEa (private to the user).

Palette/type below is still current. The **layout** was further evolved from a reference mockup the user provided afterward (centered hero with logo, `</>`-flanked headline, contact row, skills icon row, feature-chip grid, floating "code editor" / "file tree" decorative panels) — see "Home page composition" under Front-end for what actually shipped.

- **Palette:** near-black `#0b0b0f` background, warm off-white `#f4f1ea` foreground, lime accent `#c8ff00` (already in `alis-design-system`'s `tokens.css` as `--ds-color-bg` / `--ds-color-fg` / `--ds-color-accent`). Single dark theme by design choice, not light/dark toggle.
- **Type:** IBM Plex Mono for prompts, labels, data and small UI chrome; Archivo (weight ~800) for high-impact headlines, with one word/phrase set in the accent color; IBM Plex Sans for body copy. All via Google Fonts.
- **Motifs:** dot-grid background, a terminal-style prompt line, "pipeline" chips showing real facts (`lint ✓`, `test 29 ✓`, `build ✓` — pulled from actual CI/test results, never invented numbers), outline tag chips, a stat grid, a functional `⌘K` command palette as the one signature interactive/"cool" detail (not decorative animation).
- **Motion:** minimal and native-feeling — CSS transitions and the View Transitions API preferred over an animation library; respect `prefers-reduced-motion` everywhere.
- **Content strategy:** the site should demonstrate the claims (CI badge, real stack, real test count, public repos) rather than just asserting them in prose.
- **Implementation rule:** this becomes tokens + components in `alis-design-system` (fonts, command palette, pipeline/stat/tag components), not one-off Tailwind classes in `alis-portfolio/src/app/page.tsx`, so it scales to more pages later.
